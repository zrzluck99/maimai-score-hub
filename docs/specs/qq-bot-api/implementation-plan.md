# 落雪曲库与 QQ Bot 辅助 API：顺序实施计划

状态：阶段 0–3 的实现、离线验证及测试数据库演练已完成；生产历史引用核查尚未执行，阶段 4–8 待实施。当前实施范围、验证与生产核查限制见[阶段 0–3 记录](../lxns-only-catalog/verification/stages-0-3.md)。未执行生产迁移或部署。

## 1. 当前范围

以用户最后确认的撤销结果为准：

- asdfbot 保留 Provider 管理，新增 mai_hub Provider 接入本项目。
- 本项目只负责 DX NET 抓取、长期游戏好友、任务与统一成绩快照，不集中接管 asdfbot 的其他成绩 Provider、OAuth 或凭证。
- QQ 用户与好友码的长期绑定由 asdfbot 管理。
- 本项目曲库、别名、封面统一落雪，不回退到水鱼或其他源。
- 不使用 SDGB，不自动清理好友，前端暂不运行。
- 不用的功能代码保留；原始成绩、历史记录、原有接口和其他游戏行为不顺手修改。

相关设计：[落雪来源适配](../lxns-only-catalog/README.md)、[Bot API](./README.md)、[asdfbot 消费契约](./asdfbot-integration.md)。其中配置名、路径和快照存储方案是实现建议，不应将其描述为用户逐项确认过的需求。

以下阶段按顺序完成，每阶段形成独立可审查的改动与验证记录。早期改动先在测试环境验证，不在中间阶段把半套新旧数据路径部署到生产。

## 2. 第 0 阶段：基线与契约准备

目的：先固定保护对象，避免后续以“适配”为由扩大范围。

1. 检查两仓库工作区和实际运行版本。当前项目已有 shared/openapi/openapi.yaml 未提交修改，生成文档前先保留并核对，不覆盖。
2. 记录当前好友建立、任务创建/取消、成绩合并、曲库同步、导出及 asdfbot 快照替换的行为。
3. 运行相关既有测试建立基线；失败区分为已有问题或环境缺失，不修改原预期来消除失败。
4. 固定本次契约：SD 原 ID/DX +10000、普通难度 0..4、状态编码、来源键 mai_hub、完整快照范围、缺失字段和错误语义。
5. 将真实落雪样本和 asdfbot 样本整理为可离线复现的小型 fixture。补充旧曲新增 DX、小版本、宴谱和 BUDDY 场景。

产出：基线记录、契约清单、样本。验收：没有隐藏的 Provider 集中迁移；能够明确区分游戏好友关系、QQ 绑定和网站登录。

## 3. 第 1 阶段：落雪曲库转换与验证

范围：music.service.ts、lxns/transform.ts、music.schema.ts 和相关纯转换代码。

1. 使用落雪 song/list?notes=true，并显式配置目标游戏版本；从对象响应读取 songs/genres/versions。
2. 拆分 SD/DX 记录，保存 sourceSongId，保持本地 id/cid 兼容形状；保留宴谱原 ID。
3. 使用谱面显式 difficulty，版本按主版本区间归类；正确计算每组 isNew，不能统一 null。
4. 保留分类/版本来源信息、配信日期、disabled、locked；兼容旧显示名时明确只是展示映射。
5. 支持普通 Notes 与 BUDDY left/right；缺失数据不填零。不确定的 BUDDY 分数上限保持未知，待真实样本核实。
6. 完整批次校验后才允许构建候选曲库；无效响应不覆盖已验证快照、不回退旧曲库源。

产出：落雪专用转换器、候选曲库构建能力、转换测试。

验收：样本 ID/cid 无冲突；版本和新旧曲正确；宴谱不丢失；乱序、缺失、重复、错误类型和空响应有明确处理。此阶段不切换生产库。

## 4. 第 2 阶段：打通落雪唯一来源的全部依赖

范围：CoverService、MusicAliasService、ProberExportMapService、曲库缓存与相关配置。

1. 封面只从 assets2.lxns.net 获取，按 sourceSongId 定位，保留本地 PNG/WebP 输出能力。
2. 隔离旧封面缓存，防止“已有文件跳过下载”继续返回水鱼曲绘。
3. 别名只同步、聚合和返回落雪记录；旧其他来源记录可保留，但不混入结果和缓存。
4. 落雪导出直接从本地来源字段映射，不再在线请求水鱼曲库。
5. 保留水鱼成绩导出代码，但其兼容映射不能依赖水鱼歌曲元数据；无法确认映射的曲目明确报告，不能猜测或偷偷回退。
6. 保留定时曲库更新、同步锁及对外查询路径；明确版本和缓存失效规则。

产出：落雪唯一数据路径、旧缓存隔离方式、来源依赖检查。

验收：模拟水鱼不可达时，曲库、封面、别名、落雪导出仍能工作；拦截外部请求确认这些执行链无水鱼/YuzuChan 请求。失败时只返回旧的有效落雪数据或明确缺失。

## 5. 第 3 阶段：历史引用、Rating 和曲库切换演练

范围：只读差异检查工具、测试数据库切换、成绩派生字段和相关消费代码。

1. 在数据副本上比较旧曲库与落雪候选库，检查 syncs、成绩历史、任务目标 CID、封面和别名引用。
2. 输出缺失/歧义/改名/类型变化列表；不按同名猜测，不删除无法匹配的玩家历史成绩。
3. 验证 DX NET 分类+标题+类型匹配；未知曲目必须报告，不能静默丢分后认定完整。
4. 对定数、新旧曲和禁用/配信信息变化做 Rating/B50 对照。展示实际变化，并保留原始达成率、FC/FS、观测时间和历史记录语义。
5. 构建完整候选库后执行可回滚切换演练，检查各进程缓存一致性；中途失败不得留下对外可见的混合来源曲库。
6. 完成两端普通曲库版本标识的规范与一致性测试，防止仅同步时间相同就误判内容一致。

产出：引用差异报告、派生值变化报告、迁移 dry-run 与回滚步骤。

验收：没有未解释的历史引用丢失；同一来源版本可重复转换；切换失败可恢复。生产数据尚未提供时，工具和 fixture 验证继续完成，但真实数据核查明确标为未完成，不能伪造兼容结论。

## 6. 第 4 阶段：好友长期复用与停止清理

实施状态（2026-11-12）：代码与本地回归检查已完成；用户授权后已部署到本机，后端与 Worker 同时启用 retain，两端健康检查通过，Worker 六个队列消费者就绪。真实好友全流程验收待执行。详见 [第 4 阶段记录](stage-4.md)。本轮同时修复并部署了空成绩未知曲目导致的 HTTP 500。

范围：JobFriendshipService、任务分配、好友快照、Worker 好友处理器和清理入口。

1. 用现有 MongoDB 好友快照选择曾建立关系的账号；过期时核实，不要求用户再次绑定。
2. 已是好友时直接完成；已有申请时复用等待过程，不删好友后重发。
3. retain 模式停止周期 CleanupService（包含该任务的自动取消/拒绝申请），停止 shared-eligibility 触发清理和 send_request 的清理重试。
4. 底层删除操作加模式约束，防止遗漏调用路径；保留快照内部更新，不把其误当成实际删好友。
5. 新增好友检查容量，已是好友的核实/更新不占新增容量；保持现有并发分配锁和上限，不擅自扩大容量。
6. 区分账号离线、快照未知、明确无好友；真实被删后需要恢复游戏好友，但 QQ 绑定仍保留。

产出：保留好友策略、幂等好友流程、容量与异常行为测试。

验收：定时、容量不足、发送失败、重启后都不会删除既有好友；满容量老用户可以更新。legacy 模式保持既有行为，避免无关网站验证语义被修改。

## 7. 第 5 阶段：独立 DX NET 路径及基础 Bot API

范围：新增 BotApiGuard、Bot 控制器/服务、shared 契约、JobService 最小分支、SDGB/自动更新开关。

1. 增加独立 Bot 服务密钥，保留网站/管理员/Worker 原有鉴权。
2. 实现好友建立/状态、任务查询/唤醒、成绩更新和原始成绩读取接口；请求和响应白名单化。
3. 好友码级协调创建：相同活动请求复用，不同任务冲突明确报错，Bot 分支不取消旧任务。
4. Bot 更新固定 dxnet_only，找不到好友时不调用 addRival，不依赖 CabinetScoreSyncService 的机台业务；必要创建锁小范围提取后复用。
5. SDGB 及依赖它的生产者/调度支持停用；停用接口明确返回不可用，不能仍投递无人处理的任务。
6. 保留旧模块、队列、路由以及任务执行代次检查；不新增后端多 Provider 管理。

产出：基础 API、OpenAPI/契约、无 SDGB 的本地运行验证。

验收：未启动 SDGB 也能完成普通好友建立与成绩更新；无 SDGB 新任务产生；重复命令不互相取消；健康检查、Cookie 持久化和快照上报继续工作。

## 8. 第 6 阶段：asdfbot 专用完整成绩快照

范围：snapshot-jobs、snapshot、统一记录映射、完整性校验和发布存储。

1. 专用刷新明确抓取普通难度 [0,1,2,3,4]，不改变旧通用更新接口的默认难度。
2. 核实全部难度、成绩类型页面和分页完整；遗漏页面、未知歌曲、必要字段缺失时不能标 is_full=true。
3. 输出与 asdfbot 兼容的数值型 music_id/diff_index/achievements/dxscore 和固定 rank/fc/fs 编号。
4. 普通快照排除宴谱并报告数量，本项目原始宴谱能力保留。
5. 保存最后一次有效完整快照和源任务、曲库版本、成绩版本、抓取时间；失败/部分更新不替换它，旧任务不覆盖新快照。
6. profile 缺失字段不能编造；字段默认展示约定、曲库不一致和快照不完整错误必须写入契约。

产出：可安全全量导入的快照接口、跨语言 fixture、稳定错误码。

验收：部分更新永远不会冒充全量；合法空成绩与失败区分；成绩提交完成后才发布快照；重复 GET 不改变抓取时间；并发情况下数据与版本一致。

## 9. 第 7 阶段：asdfbot 接入 mai_hub

此阶段在 asdfbot 的正式工作副本中实施；当前 .reference-asdfbot 仅为静态参考，不用作部署目录。执行前读取该仓库当前约束与工作区状态。

1. 新增 MaiHubMaimaiProvider，使用统一客户端调用本项目，完成任务轮询和完整快照解析。
2. 注册 mai_hub 来源，并提供 SQLite provider CHECK 的迁移；保留旧水鱼/落雪记录和来源隔离，不改默认源。
3. 保留并接入 QQ→好友码持久化，绑定一次长期使用；错误或等待超时不清绑定。
4. 导入前校验曲库版本、记录完整性和谱面存在；按本地落雪定数计算入库 ra，保证 B50 的 SQL 预排序正确。
5. 继续使用现有事务快照替换、B50、牌子及图片能力；不迁走其他 Provider、不改其他游戏。
6. 任务轮询可恢复 jobId，网络超时和用户等待超时分开；不因重试重复发好友申请。

产出：独立 Provider、来源迁移脚本、最小命令/绑定接入、消费端回归测试。

验收：失败时 Bot 旧成绩不丢；mai_hub 不覆盖 luoxue/diving_fish 数据；好友码和本地音乐 ID 不重复转换；B50/牌子查询结果与同一快照及曲库一致。

## 10. 第 8 阶段：联调、启动配置与交付

1. 增加辅助 API 独立启动配置：backend、DX NET worker、MongoDB、Redis 及原本必要依赖；不启动前端、SDGB、Android 自动化。
2. 完成 shared/backend/worker 的适用 typecheck、build、测试和 Bot 相关测试。worker 当前无 npm test/build 脚本，按现有 Node TypeScript 测试方式运行，不能报告不存在的脚本通过。
3. 真实测试账号验证：首次申请→接受→五难度刷新→完整快照→Bot 事务导入→B50/牌子；重启后再更新无需重新绑定。
4. 验证满容量、账号离线、落雪暂不可用、抓取中断、曲库不一致、重复调用和失败恢复。
5. 整理实际通过/失败/未验证项、配置说明、迁移顺序和回滚步骤；审查无无关删除、权限变化或原始成绩语义变化。

产出：可审查的实现、验证记录、部署和迁移手册。真实好友申请、生产迁移、部署及重启按对应操作的授权执行；本计划不自动执行这些操作。

## 11. 完成条件与边界

阶段 1–3 通过后才允许切换落雪曲库；阶段 4–6 通过后才允许 asdfbot 使用新 API 做全量导入；阶段 7–8 通过后才可宣称完整接入。

所有阶段均不删除不用的旧功能、不集中迁移其他 Provider、不自动改默认来源。新增接口/配置的细节可在上述边界内调整，但变更必须反映到契约和测试。

本计划最初只涉及文档；后续“完成 0–3”任务实施了落雪适配和测试环境验证。真实生产引用核查、好友申请和部署不在已执行工作之内。
