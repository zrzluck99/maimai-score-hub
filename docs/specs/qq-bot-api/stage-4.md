# 第 4 阶段实施范围

目标：新增 `DXNET_FRIEND_POLICY=retain`，长期复用游戏好友关系并阻止自动删除。缺省 `legacy` 保持旧网站行为，未删除旧清理功能。后端与 Worker 必须使用同一模式。

现状：后端通过 MongoDB bot_statuses 保存好友快照，只有五分钟内的快照用于成绩任务直连；好友交互创建和 Worker 领取时均检查容量。Worker 周期 CleanupService、shared-eligibility 和发送失败重试会清理关系，等待接受超时会取消申请，最终均调用 MaimaiFriendApi。

顺序：

1. 修复真实抓取中的空成绩未知变体导致 500；有成绩的未知曲目仍拒绝，不能按标题猜测。
2. 引入显式 retain 模式；阻断周期清理、容量清理、发送失败清理、超时取消及底层删除/取消/拒绝 API。保留健康检查、Cookie 保存和好友快照刷新。
3. retain 下先核实是否好友、是否已有申请；已好友完成，已有申请继续等待，新的申请检查容量。失败重试只核实状态，不删关系。
4. 后端 retain 下允许用持久化好友快照选择健康 Bot，Worker 在抓取前再次核实；旧快照只用于选 Bot，不作为永久证明。已有好友交互不占新容量；新好友仍受现有容量和分配锁约束。
5. 回归 legacy 行为，验证 retain 的满容量老用户、未知快照、已有申请、失败和底层删除保护。只实现第 4 阶段，不实现第 5 阶段的独立 Bot API/SDGB 停用。

QQ 绑定仍由 asdfbot 管理，此阶段不新增或修改其数据。离线 Bot 不当作好友已删除，明确不再是好友时报恢复关系错误，不清除绑定。当前任务授权实现；除已部署 500 修复外，retain 配置和 Worker 重启不自动扩大为游戏端好友操作。

- 发送申请任务可利用该好友码在候选 Bot 上历史 `wait_acceptance` 记录定位账号，满容量时仍允许核实已有申请。历史记录可能过时，因此 Worker 若发现申请已不存在，仍必须经过实时容量检查才能新发申请。该提示不用于成绩任务或接受申请任务。
- 好友数未知、完整列表条目数与页面总数不一致时拒绝新增好友，不记录不完整快照。原有权限、心跳、队列路由、执行代次和分配锁继续保留。
